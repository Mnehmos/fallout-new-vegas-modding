# RE Knowledge Base (`research/re/`)

Recovered reverse-engineering knowledge, separated from proof-of-concept
scripts. Structure:

```
symbols.json       master symbol table: per-build, RVA-first, provenance-tagged
                   (schema v2 — confidence governed by confidence-policy.md)
confidence-policy.md  mechanical tiers; LLM judgment caps at 0.60
nvse_xrefs.json    NVSE PDB mining output: engine VA -> named NVSE context
                   (generated by scripts/re/mine_pdb.py)
functions/         Ghidra exports (functions.json, calls.json, strings.json)
                   + per-function notes for interesting recoveries
structures/        reconstructed struct layouts (TESObjectREFR, EncounterZone, ...)
signatures/        multi-fingerprint databases per build (*.fnprints.json) and
                   per-function signatures so recoveries survive patches
hypotheses/        open questions + the evidence for/against each
```

## Workflow contract

1. A question becomes a **hypothesis** file (`hypotheses/H?-slug.md`).
2. Static evidence is gathered via `scripts/re/` + Ghidra and recorded in the
   hypothesis file with VAs.
3. A function whose role is confidently identified gets an entry in
   `symbols.json` with evidence list + confidence per the scale defined there.
4. Runtime verification (x64dbg breakpoint, NVSE log, or behavioral test)
   upgrades confidence; the verification method must be recorded.
5. Reconstructed types go to `structures/` as annotated C-ish definitions.

## Seeding rule

Community knowledge (GECK wiki, NVSE plugin sources, xEdit internals) may be
recorded as evidence but must be marked `source: community-docs` — it is
corroboration, not measurement. Measured evidence (xrefs, string hits,
disassembly we read ourselves) is marked `source: static-analysis` or
`source: runtime`.
